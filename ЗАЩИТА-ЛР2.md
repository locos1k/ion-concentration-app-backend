# Защита ЛР2 — ответы на вопросы

## 1. Получение одной записи: курсор / чистый SQL / ORM

Важный нюанс терминологии: в контексте наших лаб «курсор» — это не отдельная
SQL-команда `DECLARE CURSOR`, а обиходное название для «сырого» SQL-запроса,
выполненного напрямую (без ORM), где из результата берётся одна строка
(`rows[0]`). Настоящий SQL-курсор (`DECLARE ... FETCH`) — это отдельный
механизм построчного чтения результата внутри транзакции, он в вебе почти не
используется, но полезно знать, что это такое (см. ниже).

**Через ORM** (так у нас реализовано получение растворов — `findFeedItem`,
`getDraft` в `src/solutions/solutions.service.ts`):

```ts
async getSolutionById(id: number) {
  return this.solutionRepo.findOne({
    where: { id, status: 'published' },
  });
}
```

TypeORM сам строит `SELECT ... WHERE solution_id = $1 AND status = $2 LIMIT 1`.

**Через «курсор» / чистый SQL** (у нас в этом стиле сделано удаление —
`deleteSolution`, но для примера покажем SELECT в той же логике):

```ts
async getSolutionByIdRaw(id: number) {
  const rows = await this.solutionRepo.query(
    'SELECT * FROM solutions WHERE solution_id = $1 AND status = $2 LIMIT 1',
    [id, 'published'],
  );
  return rows[0] ?? null;
}
```

`repo.query()` уходит в БД напрямую, минуя построитель запросов ORM;
результат — обычный массив строк, поэтому одну запись берём индексом `[0]`.

**Настоящий SQL-курсор** (для общего понимания, в проекте не используется):

```sql
BEGIN;
DECLARE solution_cursor CURSOR FOR
  SELECT * FROM solutions WHERE status = 'published';
FETCH NEXT FROM solution_cursor;   -- одна строка за раз
CLOSE solution_cursor;
COMMIT;
```

## 2. Получение одной записи для ленты

Метод `findFeedItem` в `solutions.service.ts`. По заданию лента должна
получать из БД сразу одну строку, без выгрузки массива и фильтрации в коде —
поэтому каждая из трёх веток (нет id / `next=true` / конкретный id) — это
ровно один вызов `findOne(...)`, который возвращает **один** раствор (а не
массив, который потом фильтруется в коде). Нюанс: из-за `relations: { likes: true }`
TypeORM под капотом делает два SQL-запроса — сначала `SELECT DISTINCT ... LIMIT 1`,
чтобы выбрать id одного раствора, и затем `SELECT ... LEFT JOIN likes ... WHERE
solution_id IN (id)`, чтобы подтянуть его вместе с лайками (с `LIMIT` прямо на
JOIN нельзя — отрезались бы строки лайков):

```ts
async findFeedItem(id: number, next: boolean) {
  let entity: Solution | null;

  if (Number.isNaN(id)) {
    // корень /solutions — первый опубликованный раствор
    entity = await this.solutionRepo.findOne({
      where: { status: 'published' },
      order: { id: 'ASC' },
      relations: { likes: true },
    });
  } else if (next) {
    // следующий после текущего id
    entity = await this.solutionRepo.findOne({
      where: { status: 'published', id: MoreThan(id) },
      order: { id: 'ASC' },
      relations: { likes: true },
    });
    if (!entity) {
      // дошли до конца ленты — заворачиваем на первый раствор
      entity = await this.solutionRepo.findOne({
        where: { status: 'published' },
        order: { id: 'ASC' },
        relations: { likes: true },
      });
    }
  } else {
    // конкретный id (переход по прямой ссылке)
    entity = await this.solutionRepo.findOne({
      where: { id, status: 'published' },
      relations: { likes: true },
    });
  }

  return entity ? this.toView(entity) : undefined;
}
```

`relations: { likes: true }` — JOIN с таблицей `likes`, чтобы количество
лайков считалось в самом запросе, а не отдельным подсчётом в коде.

## 3. Удаление одной карточки: наш вариант и вариант через ORM

**Наш вариант** — специально сырой SQL, а не ORM (так требует задание: всё
через ORM, кроме удаления):

```ts
// solutions.service.ts
async deleteSolution(id: number): Promise<void> {
  await this.solutionRepo.query(
    'UPDATE solutions SET status = $1 WHERE solution_id = $2',
    ['deleted', id],
  );
}
```

Это логическое (soft) удаление — меняется только `status`, строка из БД
физически не удаляется, каскадное удаление запрещено заданием.

**Как это же выглядело бы через ORM** (для сравнения на защите):

```ts
async deleteSolutionOrm(id: number): Promise<void> {
  await this.solutionRepo.update(id, { status: 'deleted' });
  // либо: await this.solutionRepo.update({ id }, { status: 'deleted' });
}
```

`repo.update()` под капотом сгенерирует точно такой же `UPDATE`, просто
TypeORM сам подставит имя таблицы/колонок и экранирует значения.

## 4. Написать курсор и ORM (с нуля, по требованию на месте)

Шаблон, который можно адаптировать под любое поле «на лету» (например,
попросят «получи раствор с pH больше 7»):

```ts
// ORM
async getSolutionsWithHighPh(threshold: number) {
  return this.solutionRepo.find({
    where: { status: 'published', ph: MoreThan(threshold) },
  });
}

// сырой SQL / «курсор»
async getSolutionsWithHighPhRaw(threshold: number) {
  return this.solutionRepo.query(
    'SELECT * FROM solutions WHERE status = $1 AND ph > $2',
    ['published', threshold],
  );
}
```

Логика записи одна и та же для любого запроса: у ORM-варианта условия — это
объект `where`, у сырого — строка SQL с `$1, $2...` и массив параметров
(именно `$1`, потому что драйвер `pg`, а не `?`, как в MySQL — это тоже
могут спросить отдельно).

## 5. MVC и Clean Architecture — как они видны в проекте

**MVC** в NestJS-варианте нашего проекта:

- **Model** — `Solution`/`User`/`Like` (`src/solutions/entities/*.entity.ts`,
  описывают структуру таблиц) + `SolutionsService` (бизнес-логика и доступ к
  данным: фильтрация, создание черновика, публикация, удаление)
- **View** — три Handlebars-шаблона (`views/solution-feed.hbs`,
  `views/solution-add.hbs`, `views/solution-grid.hbs`) — только разметка,
  никакой логики
- **Controller** — `SolutionsController`: разбирает HTTP-запрос
  (`@Param`, `@Query`, `@Body`), вызывает нужный метод сервиса, отдаёт
  результат вместе с именем шаблона (`@Render(...)`)

**Clean Architecture** — принцип «зависимости смотрят внутрь, к домену»,
внешние слои (фреймворк, БД, шаблонизатор) заменяемы, не должны знать о них
внутренние правила бизнес-логики. В нашем проекте это соблюдено частично:

- Контроллер тонкий, никакой бизнес-логики не содержит — только делегирует в
  сервис (хорошо соответствует принципу)
- Сервис (`SolutionsService`) содержит всю бизнес-логику отдельно от
  контроллера и от шаблонов (тоже соответствует)
- Но: сама entity (`Solution`) размечена декораторами TypeORM
  (`@Entity`, `@Column`) — то есть модель домена напрямую зависит от
  конкретного ORM-фреймворка. В «чистой» Clean Architecture домен должен быть
  вообще не знать про ORM/БД (для этого заводят отдельный DTO/доменный класс
  и отдельно — persistence-модель, между ними маппинг). У нас это упрощение
  — оправданное для лабораторной, но на защите стоит честно сказать, что
  это отступление от строгой Clean Architecture ради простоты.

## 6. Теорема CAP

CAP — про распределённые системы хранения данных: при разделении сети
(Partition) система может гарантировать **одновременно только два** из трёх
свойств:

- **Consistency (согласованность)** — все узлы отдают одинаковые (последние)
  данные
- **Availability (доступность)** — система всегда отвечает на запросы
- **Partition tolerance (устойчивость к разделению сети)** — работает, даже
  если узлы не могут связаться друг с другом

Так как сетевые разделения неизбежны в реальной распределённой системе, на
практике выбор всегда между **CP** (жертвуем доступностью ради
консистентности, как классические реляционные кластеры) и **AP** (жертвуем
консистентностью ради доступности, eventual consistency — как у многих
NoSQL/объектных хранилищ).

**В нашем проекте:** сейчас CAP напрямую не применим — у нас один инстанс
PostgreSQL и один инстанс MinIO, без репликации и без партиционирования, так
что нет ситуации «разделения сети между узлами» вообще. Теорема станет
актуальна, если систему будут горизонтально масштабировать: например,
Redis из будущей ЛР4 в кластерном режиме, или Postgres с репликами для
чтения — тогда придётся осознанно выбирать между CP и AP для каждого
хранилища.

## 7. Как реализованы publish, draft и delete

Добавление раствора — не один запрос, а два шага, каждый со своим методом.

**Шаг 1 — создание черновика** (`SolutionsController.createDraft`,
`solutions.controller.ts:27`): форма на `/solutions/draft` (когда черновика
ещё нет) отправляет `POST /solutions/draft` с одним полем — `substanceName`.
Файлы (фото/видео) в этой лабе намеренно не сохраняются.

```ts
@Post('draft')
@Redirect('/solutions/draft', 302)
async createDraft(@Body('substanceName') substanceName?: string) {
  if (substanceName?.trim()) {
    await this.solutionsService.createDraft(substanceName.trim());
  }
}
```

В сервисе (`createDraft`, `solutions.service.ts:112`) — сначала проверяем,
нет ли уже черновика у этого «создателя» (по заданию — не больше одного
черновика на пользователя), и если есть, просто ничего не создаём:

```ts
async createDraft(substanceName: string): Promise<void> {
  const existing = await this.solutionRepo.findOne({
    where: { status: 'draft', creatorId: DEFAULT_CREATOR_ID },
  });
  if (existing) return;

  // на «Далее» известны только название и медиа; описание, концентрация,
  // pH и published_at не передаём — в БД они останутся NULL
  const draft = this.solutionRepo.create({
    substanceName,
    image: '', video: '',   // файлы в ЛР2 не грузим → покажутся дефолтные
    status: 'draft',
    creatorId: DEFAULT_CREATOR_ID,
  });
  await this.solutionRepo.save(draft);
}
```

Это и есть ответ на вопрос «что заполняется по кнопке Далее»: название +
медиа (+ служебные `status`, `creator_id`, `created_at`). Всё остальное
(описание и оба поля по теме — молярная концентрация и pH, а также
`published_at`) в этот момент ещё неизвестно, поэтому в ER-диаграмме и в БД
эти поля **необязательные (nullable)**.

После редиректа обратно на `/solutions/draft` черновик уже есть, поэтому
`solution-add.hbs` рендерит вторую форму — с остальными полями и кнопкой
«Опубликовать».

**Шаг 2 — публикация** (`publishDraft` в контроллере и в сервисе,
`solutions.controller.ts:36`, `solutions.service.ts:136`): форма отправляет
`POST /solutions/draft/publish` с молярной концентрацией, pH и описанием.
Сервис находит черновик того же «создателя» и одним `UPDATE` через ORM
заполняет эти поля и меняет статус:

```ts
async publishDraft(fields: {
  molarConcentration: number; ph: number; description: string;
}): Promise<void> {
  const draft = await this.solutionRepo.findOne({
    where: { status: 'draft', creatorId: DEFAULT_CREATOR_ID },
  });
  if (!draft) return;

  await this.solutionRepo.update(draft.id, {
    ...fields,
    status: 'published',
    publishedAt: new Date(),
  });
}
```

**Удаление** (`deleteSolution`, красная кнопка «Удалить» на карточке в
`solution-grid.hbs` / `partials/solution-card.hbs`) — единственное место, где нарочно не используется ORM,
а сырой SQL `UPDATE` (логическое удаление, меняется только `status`):

```ts
@Post(':id/delete')
@Redirect('/solutions/list', 302)
async deleteSolution(@Param('id', ParseIntPipe) id: number) {
  await this.solutionsService.deleteSolution(id);
}
```
```ts
async deleteSolution(id: number): Promise<void> {
  await this.solutionRepo.query(
    'UPDATE solutions SET status = $1 WHERE solution_id = $2',
    ['deleted', id],
  );
}
```

Все три действия — обычные HTML-формы (`method="POST"`), без единой строчки
JS: браузер сам делает переход по адресу формы, а NestJS отвечает
`@Redirect(...)` — 302 обратно на нужную страницу.

## 8. Как реализована модель в коде

Модель раздвоена на два слоя, и это стоит проговорить осознанно, а не как
случайность:

**1. Entity (`src/solutions/entities/*.entity.ts`)** — описывает структуру
таблицы в БД для TypeORM. Три класса — `Solution`, `User`, `Like` — с
декораторами `@Entity`, `@Column`, `@PrimaryGeneratedColumn`, где у каждого
поля явно задано имя колонки, тип и длина/точность — один в один с
ER-диаграммой:

```ts
@Entity('solutions')
export class Solution {
  @PrimaryGeneratedColumn({ name: 'solution_id' })
  id: number;

  @Column({ name: 'name', type: 'varchar', length: 70 })
  substanceName: string;

  // nullable: у черновика (после «Далее») этих полей ещё нет
  @Column({ name: 'molar_concentration', type: 'numeric', precision: 5, scale: 3, nullable: true, transformer: numericTransformer })
  molarConcentration: number | null;

  @ManyToOne(() => User)
  @JoinColumn({ name: 'creator_id' })
  creator: User;

  @OneToMany(() => Like, (like) => like.solution)
  likes: Like[];
  // ...
}
```

Отдельный нюанс, который стоит уметь объяснить: `molar_concentration` и `ph`
в Postgres хранятся как `NUMERIC`, а драйвер `pg` возвращает `NUMERIC`
строкой (чтобы не терять точность на JS-числах). Поэтому у этих двух колонок
задан `transformer` — пара функций `to`/`from`, которая на чтении сама
переводит строку в `number` через `parseFloat` (а `NULL` у черновика
пропускает как есть), а сервис дальше спокойно сравнивает
`molarConcentration >= min` как обычные числа.

**2. View-модель (`SolutionView` в `solution.model.ts`)** — это уже не то,
что лежит в БД, а то, что реально уходит в шаблон: помимо полей raствора там
есть вычисляемые `imageUrl`/`videoUrl` (готовая ссылка на файл), `likesCount`
(посчитанное число лайков) и `descriptionShort`/`descriptionRest` (описание,
уже разрезанное для «Ещё», см. вопрос 9). Собирает её приватный метод
`toView()` в сервисе — он единственное место, где entity превращается в то,
что видит пользователь.

Разделение осознанное: entity знает только про БД, view-модель — только про
то, что нужно шаблону, и между ними явный маппинг (`toView`), а не смешение
всего в одном классе.

## 9. Как реализовано «Ещё» (без JavaScript)

Задача: у длинного описания на ленте видно только 2 строки, и есть кнопка
«Ещё», разворачивающая остальное — без JS. Решение — нативный HTML-тег
`<details>`/`<summary>`, у которого раскрытие/схлопывание встроено в
браузер:

```hbs
<!-- solution-feed.hbs -->
<div class="description">
  {{solution.descriptionShort}}
  {{#if solution.descriptionRest}}
    <details class="desc-more">
      <summary></summary>
      {{solution.descriptionRest}}
    </details>
  {{/if}}
</div>
```

Текст заранее разрезан на сервере — приватный метод `splitDescription` в
`solutions.service.ts` (используется внутри `toView`) отдаёт готовую пару
«видимая часть» / «скрытая часть»:

```ts
private splitDescription(text: string): [string, string] {
  if (text.length <= DESCRIPTION_HEAD) return [text, ''];
  let cut = text.lastIndexOf(' ', DESCRIPTION_HEAD);
  if (cut < DESCRIPTION_HEAD * 0.6) cut = DESCRIPTION_HEAD;
  return [text.slice(0, cut), text.slice(cut)];
}
```

`DESCRIPTION_HEAD = 65` символов — подобрано так, чтобы влезало ровно 2
строки в колонку ленты. Режем не строго по символу, а по последнему пробелу
перед границей (`lastIndexOf(' ', ...)`), чтобы не разрывать слово
пополам; если пробела рядом не нашлось (очень длинное слово), просто режем
по границе как есть.

Слово «Ещё»/«Свернуть» — это не текст в HTML, а CSS-генерируемый контент на
`<summary>` через `::after`, что и переключается атрибутом `[open]`,
который сам браузер вешает на `<details>` при клике:

```css
.desc-more > summary::after { content: ' Ещё'; }
.desc-more[open] > summary::after { content: ' Свернуть'; }
```

## 10. Где и как считаются лайки

**Хранение.** Лайки — это строки таблицы `likes` (`like_id`, `user_id`,
`solution_id`): одна строка = один лайк одного пользователя на один раствор
(связь многие-ко-многим между `users` и `solutions` через `likes`). Отдельного
поля «количество лайков» в `solutions` нет — число не хранится, а вычисляется
при каждом показе.

**Связь в коде** (`src/solutions/entities/solution.entity.ts`, внизу):

```ts
@OneToMany(() => Like, (like) => like.solution)
likes: Like[];
```

Обратная сторона — `@ManyToOne` с `solution_id` в `like.entity.ts`.

**Загрузка.** Во всех трёх запросах растворов (`findFeedItem`, `getDraft`,
`getAllPublished` в `solutions.service.ts`) указано `relations: { likes: true }`.
TypeORM делает `LEFT JOIN likes` — вот реальный SQL каталога:

```sql
SELECT "Solution"."solution_id", "Solution"."name", ... ,
       "Solution__Solution_likes"."like_id",
       "Solution__Solution_likes"."user_id",
       "Solution__Solution_likes"."solution_id"
FROM "solutions" "Solution"
LEFT JOIN "likes" "Solution__Solution_likes"
       ON "Solution__Solution_likes"."solution_id" = "Solution"."solution_id"
WHERE "Solution"."status" = $1
ORDER BY "Solution"."solution_id" ASC
```

`LEFT JOIN` (а не `INNER`), чтобы раствор без лайков тоже попал в выборку — с
пустым массивом `likes` и счётчиком 0.

**Подсчёт** — в `toView()` (`solutions.service.ts`), одной строкой:

```ts
likedBy: s.likes.map((like) => like.userId),
likesCount: s.likes.length,
```

То есть считаем в приложении: БД отдаёт строки лайков, `s.likes.length` — их
количество. Дальше `likesCount` идёт в шаблон (`{{likesCount}}` в
`partials/solution-card.hbs` и `{{solution.likesCount}}` в `solution-feed.hbs`).

**Что сказать, если спросят «почему не COUNT в SQL».** Сейчас подсчёт в коде по
длине массива — для лабораторной с единицами лайков это нормально и заодно даёт
список `likedBy`. При большом числе лайков выгоднее считать в БД, чтобы не
таскать все строки. Тот же результат без выгрузки лайков:

```ts
// ORM: счётчик подтягивается подзапросом, строки лайков не загружаются
const solutions = await this.solutionRepo
  .createQueryBuilder('s')
  .loadRelationCountAndMap('s.likesCount', 's.likes')
  .where('s.status = :status', { status: 'published' })
  .getMany();
```
```sql
-- или чистый SQL
SELECT s.solution_id, COUNT(l.like_id) AS likes_count
FROM solutions s
LEFT JOIN likes l ON l.solution_id = s.solution_id
WHERE s.status = 'published'
GROUP BY s.solution_id;
```

Ставить и снимать лайки пока нельзя — это `POST like` из лабы 3; сейчас лайки
только читаются из БД (строки добавляются вручную через `seed.sql`/Adminer).
