### 1. Перечислить все 10 запросов

Адреса начинаются с `/api`. Три GET (по заданию): список, лента, черновик.

| № | Домен | Метод | URL | Что делает |
|---|---|---|---|---|
| 1 | растворы | GET | `/api/solutions?min=&max=` | список опубликованных растворов с фильтром по молярной концентрации; в каждом растворе признак `isCreator` (0/1) |
| 2 | растворы | GET | `/api/solutions/feed` и `/api/solutions/feed/:id?next=true` | лента опубликованных: без `id` — первый раствор, с `id` — этот раствор, с `next=true` — следующий |
| 3 | растворы | GET | `/api/solutions/draft` | черновик текущего пользователя (не больше одного, `id` не указывается) |
| 4 | растворы | POST | `/api/solutions` | добавление черновика: название + файлы `image` и `video` (`multipart/form-data`), файлы уходят в MinIO под латинскими именами |
| 5 | растворы | PUT | `/api/solutions/:id/publish` | публикация: `draft` → `published`, плюс описание, концентрация и pH |
| 6 | растворы | DELETE | `/api/solutions/:id` | мягкое удаление (статус `deleted`), только своих растворов |
| 7 | растворы | POST | `/api/solutions/:id/like` | лайк от текущего пользователя: `value: 1` ставит, `0` отменяет |
| 8 | пользователь | POST | `/api/users` | регистрация (пароль хранится как `соль:хеш`) |
| 9 | пользователь | POST | `/api/auth/login` | аутентификация (заглушка до ЛР4) |
| 10 | пользователь | POST | `/api/auth/logout` | деавторизация (заглушка до ЛР4) |

Лента — это один метод (один обработчик `@Get(['feed', 'feed/:id'])`), у которого `id`
необязательный, поэтому GET ровно три.

Если спросят про коды ответов: `200` — успех, `201` — создано (POST раствора и
регистрация), `204` — удалено, без тела, `400` — неверные данные, `403` — чужой раствор,
`404` — не найден, `409` — конфликт (второй черновик, логин занят, недопустимая смена статуса).

### 2. Функция лайка из кода

Запрос `POST /api/solutions/:id/like` с телом `{ "value": 1 }` (поставить) или `{ "value": 0 }` (отменить).

**Контроллер** (`src/solutions/solutions-api.controller.ts`) — принимает запрос и отдаёт
ответ, логики в нём нет:

```ts
@Post(':id/like')
@HttpCode(HttpStatus.OK)
async like(
  @Param('id', ParseIntPipe) id: number,
  @Body() dto: LikeSolutionDto,
): Promise<SolutionResponseDto> {
  return this.serialize(await this.solutionsService.setLike(id, dto.value));
}
```

**DTO** (`src/solutions/dto/like-solution.dto.ts`) — проверяет, что `value` равно 0 или 1:

```ts
export class LikeSolutionDto {
  @Type(() => Number)
  @IsIn([0, 1], { message: 'value: 1 — поставить лайк, 0 — отменить' })
  value: 0 | 1;
}
```

**Сервис** (`src/solutions/solutions.service.ts`) — сама функция лайка:

```ts
async setLike(id: number, value: 0 | 1): Promise<SolutionView> {
  const userId = getCurrentUser().id;
  const entity = await this.solutionRepo.findOne({
    where: { id, status: 'published' },
    relations: { likes: true },
  });
  if (!entity) throw new NotFoundException(`Раствор ${id} не найден`);

  const existing = entity.likes.find((like) => like.userId === userId);
  if (value === 1 && !existing) {
    await this.likeRepo.save(this.likeRepo.create({ userId, solutionId: id }));
  } else if (value === 0 && existing) {
    await this.likeRepo.delete(existing.id);
  }
  return this.loadView(id);
}
```

**Как работает, по шагам:**

1. `getCurrentUser().id` — берём текущего пользователя из функции-singleton (константа).
2. Ищем раствор по `id` **только среди опубликованных** (`status: 'published'`) вместе с его
   лайками (`relations: { likes: true }`). Не нашли (нет такого, черновик или удалён) — `404`.
3. Ищем среди лайков раствора лайк текущего пользователя (`existing`).
4. `value === 1` и лайка ещё нет — создаём строку в таблице `likes` (`user_id`, `solution_id`).
5. `value === 0` и лайк есть — удаляем эту строку.
6. В остальных случаях ничего не делаем: повторный `1` не создаст второй лайк, а `0` без
   лайка ничего не сломает (метод идемпотентный).
7. `loadView(id)` заново читает раствор из БД, поэтому в ответе актуальные `likesCount` и
   `isLiked`.

Таблица `likes` — связь «многие ко многим» между `users` и `solutions` (поля `like_id`,
`user_id`, `solution_id`). Ограничения уникальности на пару (`user_id`, `solution_id`) в БД
нет, дубли предотвращает проверка в коде (шаг 3–4).

### 3. Список параметров в ленте

Запрос ленты: `GET /api/solutions/feed` и `GET /api/solutions/feed/:id?next=true`.
Тела запроса нет, заголовков для работы не нужно.

| Параметр | Где | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `id` | path | целое число | нет | идентификатор раствора; без него возвращается первый опубликованный. Не число — `400` |
| `next` | query | boolean (`true` / `false`) | нет, по умолчанию `false` | `true` — вернуть раствор, следующий за `id`. Другое значение — `400` |

Других параметров нет: лишний query-параметр (например, `?foo=1`) даёт `400`
(`property foo should not exist`) из-за валидации `whitelist` + `forbidNonWhitelisted`.

Как параметры влияют на результат (проверено запросами):

| Запрос | Результат |
|---|---|
| `/feed` | первый опубликованный раствор (id 1) |
| `/feed?next=true` | то же самое: `next` без `id` ничего не значит |
| `/feed/1` или `/feed/1?next=false` | раствор с id 1 |
| `/feed/1?next=true` | следующий за 1 — раствор id 2; после последнего опубликованного лента идёт по кругу, снова на первый |
| `/feed/6` (удалён) или `/feed/5` (черновик) | `404`, лента отдаёт только опубликованные |
| `/feed/1?next=abc` | `400` |

Выбор записи в БД — один запрос `findOne` на каждую ветку (метод `findFeedItem` в
`solutions.service.ts`), без выгрузки массива и фильтрации в коде.

Что возвращает лента (один раствор): `id`, `substanceName`, `description`,
`molarConcentration`, `ph`, `imageUrl`, `videoUrl`, `likesCount`, `isLiked`, `isCreator`, `status`.

## Контрольные вопросы

Веб-сервисы, REST, SOA». Места, которых в лекциях нет, помечены.

### Что такое веб-сервис

- **API** — описание способов взаимодействия одной программы с другими: набор компонентов
  (функций), с помощью которых программа (бот, сайт) может использовать другую программу.
  **Веб API** реализуется веб-сервисом.
- **Веб-служба (веб-сервис)** — идентифицируемая уникальным веб-адресом (URL) программная
  система со стандартизированными интерфейсами. Веб-службы взаимодействуют друг с другом
  и со сторонними приложениями по протоколам (SOAP, JSON-RPC и т. д.) и соглашениям (REST).
  Веб-служба — единица модульности сервис-ориентированной архитектуры.
- Зачем нужен: чтобы использовать веб-сервер как универсальный источник данных для других
  приложений (React-фронтенд, нативное и мобильное приложение). Данные получаем не как HTML,
  а структурированно в формате **JSON** (он заменил XML как формат данных для HTTP-методов).
  Получается трёхзвенная архитектура: фронтенд — веб-сервис — БД.
- У нас: в ЛР1–2 приложение отдавало HTML-страницы, в ЛР3 появился веб-сервис с адресами
  `/api/...`, который отдаёт и принимает JSON.

### REST и его требования

**REST** (Representational State Transfer) — набор правил того, как организовать код
серверного приложения, чтобы все системы легко обменивались данными и приложение можно было
масштабировать. Предложил Рой Филдинг для HTTP. **RESTful** — веб-службы, не нарушающие
ограничений:

1. **Клиент-сервер** — клиент и сервер разделены («дорога нас не спрашивает»).
2. **Отсутствие состояния** — каждый запрос самодостаточен («не важно, откуда едем»).
3. **Кэширование** — ответ можно сохранить на клиенте («запомнить дорогу»).
4. **Единообразие интерфейса** — самое сложное: правильно оформить методы и адреса.
5. **Слои** — проксирование, балансировка («смотрим на дорогу, знаки, разметку»).
6. **Код по требованию** — например, JS в браузере («как навигатор»).

**Правила именования REST API** (лекция 5): в URL указываем домен (группу методов), название
метода и идентификаторы; обязательно начало `/api`. Правила: 1) конечные точки — существительные,
не глаголы; 2) множественное число; 3) документация; 4) версия приложения; 5) пагинация;
6) SSL; 7) HTTP-методы; 8) эффективное использование кодов ответов HTTP.

У нас: `/api/solutions` — существительное во множественном числе, конкретный раствор —
`/api/solutions/:id`; методы HTTP соответствуют действиям, результат передаётся кодами
(`200`, `201`, `204`, `404` и т. д.). Адрес `/:id/publish` содержит глагол: публикация сделана
отдельным методом (`PUT`), как требует задание (слайд «Методы по вашей теме»).

### RPC

- **RPC** (remote procedure call) — удалённый вызов процедур.
- Реализация включает два компонента: **сетевой протокол** для обмена в режиме
  клиент-сервер и **язык сериализации** объектов (структур).
- Варианты: **JSON-RPC** (кодирует сообщения в JSON; через него работает AJAX), **XML-RPC**
  (более сложный вариант — SOAP), **gRPC**.
- **gRPC** — система RPC с открытым исходным кодом, разработана в Google
  (аутентификация, двунаправленная потоковая передача, управление потоком). Транспорт —
  **HTTP/2**, язык описания интерфейса — **Protocol Buffers**.
- **AJAX** — подход к построению интерактивных интерфейсов: «фоновый» обмен данными браузера
  с веб-сервером, страница не перезагружается полностью.
- Отличие от REST (вывод из лекции): REST описывает ресурсы по адресам и стандартные методы
  HTTP; RPC — вызов процедуры с сериализованными параметрами.

### Заголовки и методы HTTP

**HTTP** — протокол передачи гипертекста (сейчас — для произвольных данных). Клиент-серверный:
клиент (потребитель) инициирует взаимодействие, сервер (поставщик) ждёт запрос, обрабатывает и
возвращает ответ. Из-за этого неудобно получать уведомления и сообщения чата. Протокол **без
хранения состояния** между запросами, но компоненты могут хранить куки (клиент) или сессии
(сервер).

Запрос и ответ состоят из: **методов** (GET, POST, PUT…), **кодов состояния** (200 OK,
404 Not Found) и **заголовков** (формат «параметр: значение»). В лекции заголовки даны только
как общее определение; из примеров по лабе: `Content-Type` (`application/json` или
`multipart/form-data` при загрузке файлов) и `Location` (куда перенаправить при коде 3xx —
так работают наши формы на страницах).

**Методы** (лекция 4):

| Метод | Назначение по лекции | У нас |
|---|---|---|
| GET | запрос содержимого ресурса («select») | список, лента, черновик |
| POST | передача ресурсу данных пользователя («insert») | создание раствора, лайк, регистрация, вход, выход |
| PUT | загрузка содержимого запроса на ресурс («update») | публикация |
| PATCH | PUT к фрагменту ресурса (например, статус) | не используем |
| DELETE | удаление ресурса | мягкое удаление |
| OPTIONS, HEAD, TRACE, CONNECT | служебные | не используем |

**Коды состояния:**

| Код | Класс | Назначение |
|---|---|---|
| 1xx | информационный | информирование о процессе передачи |
| 2xx | успех | запрос принят и обработан |
| 3xx | перенаправление | нужен другой запрос, обычно по другому URI; адрес указан в заголовке `Location` |
| 4xx | ошибка клиента | ошибка со стороны клиента |
| 5xx | ошибка сервера | неудачное выполнение по вине сервера |

У нас используются `200`, `201`, `204`, `400`, `403`, `404`, `409`. По лекции для Go: в тело
ответа не добавлять «status», передавать только коды состояний (200/404).

**URI:** схема HTTP — `http://хост:порт/путь?параметры#якорь`, порт по умолчанию 80.
Пример: `http://iu5.bmstu.ru:8080/cat1/cat2/script.asp?param1=1&param2=2#anchor1`.

### Версии HTTP

- **1991, HTTP/0.9** — только GET.
- **1996, HTTP/1.0** — появился POST и другие методы, заголовки, кэширование.
- **1999, HTTP/1.1** — keep-alive, заголовок `Host` (виртуальный хостинг).
- **2015, HTTP/2** — на основе SPDY: бинарный, сжатие заголовков, мультиплексирование,
  приоритезация ресурсов, отмена загрузки, Server Push. Появились потоки (streams) в рамках
  одного TCP-соединения для всего содержимого страницы; проблема — потеря одного пакета
  тормозит поток, особенно в беспроводных сетях. HTTP/2 — транспорт для gRPC.
- **HTTP/3** (draft) — на основе **QUIC**: отказ от TCP, переход на UDP (заголовки UDP проще);
  QUIC сочетает потоки, TLS и гарантированную доставку; появился из-за развития беспроводных
  сетей и проблем в стеке (миграция IP и т. д.), есть идентификатор соединения.
  В HTTP/2 все файлы идут в одном соединении, в QUIC — несколько потоков для разных файлов,
  поэтому ожидание третьего файла не мешает обрабатывать первые два.

### HTTPS

**HTTPS** — протокол на основе **TLS** (ранее SSL), работает поверх TLS и TCP, порт по
умолчанию **443**; разработан в 1994 году в Netscape. Обеспечивает:

- **аутентификацию** — асимметричное шифрование через сертификаты, с его помощью
  передаётся session key (сеансовый ключ);
- **конфиденциальность** — симметричное шифрование с помощью полученного ранее session key.

Для сравнения: HTTP — поверх TCP, HTTP/3 — поверх QUIC. У нас локально приложение работает
по обычному HTTP.

### Модель OSI (ISO) и TCP/IP

**7 уровней модели OSI** (лекция 4):

| № | Уровень | Суть |
|---|---|---|
| 7 | Прикладной | приложения (браузер, веб-сервер, мобильные приложения) |
| 6 | Представления | форматы данных: HTML, mp4 и т. д. |
| 5 | Сеансовый | соединение в TCP |
| 4 | Транспортный | делит сообщение на универсальные сегменты |
| 3 | Сетевой | позволяет найти устройство (IP как почтовый адрес) |
| 2 | Канальный | организация канала (сегмент Wi-Fi) + постоянный MAC-адрес («как паспорт») |
| 1 | Физический | среда передачи: какие провода, длина волны света |

Уровни 4–3–2 — как матрёшка: **сегмент — пакет — кадр**.

**Модель TCP/IP** — стек протоколов, на котором базируется Интернет. TCP и IP появились с
самого начала и находятся в середине стека — это основа глобальной сети. Для приложений могут
быть разные протоколы (HTTP, FTP, SMTP…), физическая среда тоже может быть разной.

Стандарты Интернета открыты: их разрабатывает **IETF**, документы называются **RFC**
(для URL, HTTP, FTP и др.).

Наш запрос: HTTP (прикладной) → TCP, порт 3000 (транспортный) → IP, `localhost` (сетевой)
→ канальный и физический уровни.
